# Доказательства из прогонов

Три прогона стенда (по 30 с, два клиента, шумной контент, `LOBBY=0`).
Клиенты ходят на приватный адрес машины — тогда `moonlight-common-c`
не каптит размер RTP-пакета, как это делает для VPN-адреса сервера.

| каталог | размер пакета | path MTU | результат |
|---|---|---|---|
| `mtu-A` | 1392 | без ограничения | видео идёт: 1667 / 1678 кадров |
| `mtu-B` | 1392 | 1420 | **0 кадров, обрыв соединения кодом -100 через 10.6 с** |
| `mtu-C` | 1024 | 1420 | видео идёт: 1641 / 1669 кадров |

Внутри каждого каталога:

* `client-A.json`, `client-B.json` — метрики клиента: кадры, I-кадры,
  пропуски, код завершения, время сборки кадра;
* `wolf-payload.txt` — что wolf реально ставил в payloader
  (`payload_size=…`) и сколько раз форсировал IDR;
* `analysis.txt` — разбор pcap прогона (если пакет захватывался).

Прогон `mtu-A` дополнительно дал wire-замер: **13 550 IP-пакетов ровно
по 1436 байт** (UDP-датаграмма 1408 байт + 28 байт заголовков) — при path
MTU 1420 все они не влезают. В прогоне `mtu-B` на проводе остаётся только
управляющий трафик, видеопакетов с порта 48110 — ноль.

Сам pcap (десятки мегабайт) и клиентские сертификаты в репозиторий не
попадают: pcap локальный и воспроизводится, сертификаты — секреты.

Прогоны сделаны на сборке wolf из upstream master (sha `db709cf`);
дефолт в скриптах стенда — тот же публичный образ
`ghcr.io/games-on-whales/wolf:sha-db709cf`, переопределяется через
`WOLF_IMAGE`. Тег `main` в том же реестре на момент прогона не проходил
фазу `/launch` (клиент получал `error code: 125 — Operation canceled`),
поэтому версия закреплена по sha, а не по имени ветки.
