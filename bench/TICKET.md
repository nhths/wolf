# wolf: видео не идёт к клиенту за VPN — RTP-пакеты не влезают в path MTU

## Симптом

Клиент (MacBook, планшет) подключается к wolf через WireGuard: пейринг
проходит, поток стартует, управляющий канал живёт — но **видео не идёт
вообще**. Через ~10 секунд клиент рвёт соединение сам («no video traffic
was ever received from the host»).

По LAN те же клиенты работают.

## Причина

Размер RTP-пакета выбирает клиент, и для «приватного» адреса сервера он
не каптится.

`moonlight-common-c`, `Connection.c`:

```c
if (StreamConfig.streamingRemotely == STREAM_CFG_AUTO) {
    if (!isNat64 && isPrivateNetworkAddress(&RemoteAddr)) {
        StreamConfig.streamingRemotely = STREAM_CFG_LOCAL;   // ← «мы в своей сети»
    }
    else {
        StreamConfig.streamingRemotely = STREAM_CFG_REMOTE;
        if (RemoteAddr.ss_family == AF_INET || isNat64) {
            StreamConfig.packetSize = 1024;   // ← кап, чтобы не фрагментировать
        }
    }
}
```

`isPrivateNetworkAddressV4()` (`PlatformSockets.c:640`) считает приватными
10/8, 172.16/12, 192.168/16, 169.254/16. **Loopback (127/8) в список не
входит**, а адрес WireGuard-сервера (172.26.0.x) — входит.

Дальше по цепочке:

1. адрес сервера приватный → клиент считает его локальным → **пакет в
   1024 байта не каптится**, в RTSP SETUP уходит
   `x-nv-video[0].packetSize=1392`;
2. wolf берёт это значение как есть —
   `src/moonlight-server/rtsp/commands.hpp:230`:
   `.packet_size = args["x-nv-video[0].packetSize"].value_or(1392)`;
3. payloader режет RTP-пакеты по `payload_size` минус заголовок
   (`gst-plugin/video.hpp`), wolf кладёт в пакет
   `32 (RTP+NV) + 1392 = 1408` байт полезной нагрузки;
4. IP-пакет получается `1408 + 28 = 1436` байт;
5. path MTU до VPN-клиента — **1420** (WireGuard). 1436 > 1420: пакет
   не влезает, а туннель не фрагментирует — **пакет исчезает целиком**;
6. RTP-пакеты не приходят вообще → клиент не видит ни одного кадра →
   через `x-nv-video[0].timeoutLengthMs` (7000 мс) рвёт соединение.

Управляющий канал при этом жив: ping'и и RTSP — мелкие пакеты, они
проходят.

## Доказательства

Стенд: `bench/` в форке `nhths/wolf`, ветка `feat/testbench`. Локальный
вариант гоняет настоящих Moonlight-клиентов (`moonlight-common-c`)
против wolf в podman; «VPN-линк» эмулируется на loopback.

Прогоны (по 30 с, два клиента, шумной контент, `LOBBY=0`):

| # | размер пакета | path MTU | клиент видит | итог |
|---|---|---|---|---|
| A | 1392 (адрес приватный → клиент не капнул) | без ограничения | 1667 / 1678 кадров | работает |
| B | 1392 | 1420 | **0 кадров, соединение прервано кодом -100 через 10.6 с** | **воспроизведено** |
| C | 1024 (клиент капнул сам) | 1420 | 1641 / 1669 кадров | работает |

Разница между B и C — только в размере пакета; разница между B и A —
только в MTU.

Замер на проводе (pcap, прогон A): **13 550 IP-пакетов ровно по 1436
байт** (UDP-датаграмма 1408 байт + 28 байт заголовков) при path MTU 1420 —
то есть все видеопакеты не влезают в туннель.

В прогоне B на проводе остаётся только управляющий трафик (пинги на
47999/48210), видеопакетов с порта 48110 — **ноль**.

Поведение клиента видно и в его логе: без капа
(`Packet size capped at 1024 bytes for remote IPv4 streaming`) — при
адресе 127.0.0.1; с приватным адресом 192.168.31.241 этой строки нет,
то есть пакеты остаются 1392-байтными.

## Что НЕ является причиной

* **Выбрасывание кадров в лобби.** Гипотеза «общий producer роняет кадры»
  механически неверна: номер кадра (`frameIndex`) присваивает payloader
  (`rtpmoonlightpay->frame_num++` на каждый *входной* буфер), поэтому
  просадка producer'а снижает fps, но **не создаёт пропусков в
  номерах кадров**. Пропуск в `frameIndex` бывает только при потере уже
  пронумерованных пакетов — то есть в транспорте или при выбрасывании
  пакетов в appsink. Локально лобби (общий producer) против двух
  отдельных producer'ов при одинаковой нагрузке даёт одинаковый
  результат: 0 пропусков, 0 шторма IDR.
* **Конфиг wolf.** Секция `[gstreamer]` на боевом хосте совпадает с
  шаблоном репозитория (`src/moonlight-server/state/default/config.v7.toml`)
  дословно.
* **Битрейт.** wolf не режет поток под заявленный клиентом.

## Что можно чинить

1. **Клиент (moonlight-common-c).** `isPrivateNetworkAddress` — слишком
   грубая проверка: адрес в той же приватной сети ещё не значит «мы
   локально». Правильнее сравнивать подсеть (как делает сам
   `isLocalAddress` в moonlight-qt), иначе любой VPN-адрес 10/8,
   172.16/12, 192.168/16 отключает кап размера пакета.
2. **Сервер (wolf).** Размер пакета берётся из клиента без проверки;
   сервер не знает path MTU клиента, но может не отдавать пакеты
   больше заведомо безопасного предела (например, `payload_size=1360` →
   IP-пакет 1400 байт влезает в MTU 1420).
3. **Сеть.** Поднять MTU интерфейса WireGuard (≥1452), если это
   допустимо.

## Воспроизведение

```sh
cd bench
./scripts/build.sh

# воспроизведение: клиент с приватным адресом + path MTU 1420
NOISE=1 HOST=192.168.31.241 PACKET_SIZE=1392 ./scripts/run-local.sh up
bash scripts/link-mtu.sh on 1420 48110
HOST=192.168.31.241 PACKET_SIZE=1392 LOBBY=0 DURATION=30 \
  ARTIFACTS=$PWD/artifacts/mtu-B ./scripts/run-local.sh run
# → клиент: 0 кадров, соединение прервано (-100)
bash scripts/link-mtu.sh off
```

Контроль: тот же прогон с `PACKET_SIZE=1024` или без `link-mtu.sh` —
видео идёт штатно.

`NOISE=1` при подъёме wolf обязателен: на статичном градиенте кодировщик
даёт мелкие кадры, последний RTP-пакет кадра получается короче 1392
байт и влезает в MTU — тест тогда ничего не проверяет.

Артефакты каждого прогона (логи клиентов, лог wolf, pcap и его разбор)
складываются в `ARTIFACTS`; в репозиторий они не попадают.
